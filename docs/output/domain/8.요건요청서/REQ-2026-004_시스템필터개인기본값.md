## 2. 요청 배경 및 목적

### 2.1 요청 배경

변경 관리(`/requests`)·배포 관리(`/deploys`)에 운영시스템 Select 가 들어갔지만(REQ-2026-002·003) 초기값이 항상 "전체"라, 자기 시스템만 보는 담당자는 화면에 들어올 때마다 시스템을 다시 골라야 한다. 한편 포탈에는 이미 **시스템 담당자 배정**(시스템 관리 > 담당자 패널, `system_managers` 테이블)이 있고, 두 화면 모두 로그인 사용자의 담당 시스템 ID 목록을 `GET /api/systems/managed` 로 받아 승인 권한 판단에 쓰고 있다 (`FE/pages/ChangeRequest/index.tsx:94·181`, `FE/pages/DeployRequest/index.tsx:101·510·781`). 즉 "이 사용자가 어느 시스템 담당인가"는 이미 알고 있는데 필터 초기값에는 쓰지 않는다.

검토한 대안 (2026-11-04):

| 안 | 내용 | 판단 |
|---|---|---|
| ① 마지막 선택 저장 | localStorage 에 사용자별로 기억 | **채택** — 프론트만, 담당이 여러 개인 사용자를 메움 |
| ② 사용자 속성 추가 | `User.defaultSystemId` 컬럼 + 설정 화면 | 기각 — DB 컬럼 추가(마이그레이션 도구 없음), 설정 화면 신설, 담당자 데이터와 이중 관리 |
| ③ 최근 기록 조회 | 최근 요청의 시스템을 추론 | 기각 — 기준 모호, 조회 로그 없음 |
| ④ 담당 시스템 기본값 | 담당 시스템이 1개면 그것 | **채택** — 데이터·관리 UI·API 가 이미 있고 스키마 변경 없음 |

### 2.2 기대 효과

- 담당자는 화면에 들어오면 바로 자기 시스템 목록·현황을 본다. 시스템 관리에서 담당자만 등록해 두면 된다
- 담당 시스템이 여럿이거나 담당이 아닌 사용자도 한 번 고르면 다음부터 그대로다
- 운영시스템이 늘어날수록(서비스정의서 시나리오 5) 효과가 커진다

## 4. 업무 흐름

### 4.1 현재 업무 흐름 (As-Is)

1. 변경 관리 또는 배포 관리 진입 → 시스템 Select "전체"
2. 담당자가 매번 자기 시스템을 고름 → 목록·현황이 그 시스템 기준
3. 다른 메뉴 갔다 돌아오면 다시 "전체"

### 4.2 변경 후 업무 흐름 (To-Be)

1. 진입 시 Select 초기값을 다음 순서로 정한다
   1. 이 브라우저에 **이 사용자가 마지막으로 고른 값**이 있고, 그 시스템이 지금 활성 목록에 있으면 → 그 값 ("전체"를 골랐던 것도 포함)
   2. 없으면, 로그인 사용자의 **담당 시스템이 정확히 1개**면 → 그 시스템
   3. 그 외(담당 0개·2개 이상, 저장값 없음) → "전체"
2. 사용자가 Select 를 바꾸면 그 값을 사용자별로 저장한다. 이후 진입·탭 전환·다른 메뉴 왕복 모두 저장값이 우선
3. 목록·배지·현황 탭 동작은 현행(REQ-2026-002·003)과 같다

## 6. 예외 및 특수 상황

| 상황 | 처리 방식 |
|---|---|
| 네트워크 단절 시 | 담당 목록 조회 실패 → 담당 규칙은 건너뛰고 저장값 → 전체. 목록 로딩 실패 표시는 현행 |
| 중복 요청 발생 시 | 해당 없음 |
| 권한 없는 접근 시 | 변경 없음. EXTERNAL 은 담당 배정이 없으므로 저장값 → 전체 |
| 저장된 시스템이 비활성화된 경우 | 무시 → 담당 1개 규칙 → 전체 (5절 #5) |
| 담당 시스템이 비활성화된 경우 | `/systems/managed` 가 비활성도 돌려주면 활성 목록과 교집합을 낸 뒤 1개 판단 |
| 담당 배정이 바뀐 경우 | 다음 진입부터 새 담당 기준. 단 저장값이 있으면 저장값 우선 — 사용자가 한 번 바꾸면 됨 |
| 다른 PC·브라우저 | 저장값 없음 → 담당 1개 규칙 → 전체. 서버 저장은 하지 않음(②기각) |
| localStorage 사용 불가(사생활 보호 모드 등) | 저장 실패를 무시하고 담당 규칙 → 전체. 오류 표시 없음 |
