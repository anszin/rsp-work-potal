## 2. 요청 배경 및 목적

### 2.1 요청 배경

변경 관리 화면(`/requests`)은 전 운영시스템의 변경 요청을 한 목록에 보여 주고, 필터는 상태뿐이다. 운영시스템이 2개이고 더 늘어날 예정이라, 담당 시스템의 요청만 보려면 목록에서 눈으로 골라야 한다. 백엔드 `GET /api/change-requests?systemId=` 와 프론트 API 함수(`getChangeRequests({ systemId })`)는 이미 시스템 조건을 받지만 화면이 쓰지 않는다. (현행분석서 7.1절, `FE/pages/ChangeRequest/index.tsx:82`, `FE/api/changeRequests.ts:73`)

### 2.2 기대 효과

- 시스템 담당자가 자기 시스템의 변경 요청만 바로 본다. EXTERNAL(요청자)도 자기가 올린 시스템만 고를 수 있다
- 운영시스템이 늘어나도 목록이 섞이지 않는다 (서비스정의서 시나리오 5 "운영시스템 추가" 전제)
- 상태 필터와 조합해 "A 시스템의 승인 대기" 같은 조회가 된다

## 4. 업무 흐름

### 4.1 현재 업무 흐름 (As-Is)

1. 변경 관리 메뉴 진입 → 전 시스템 변경 요청 목록
2. 상태 버튼으로 필터 → 페이지네이션
3. 현황 탭은 시스템별 건수를 집계만 보여 줌

### 4.2 변경 후 업무 흐름 (To-Be)

1. 변경 관리 메뉴 진입 → 상단에 **시스템 선택**(전체 / 시스템 A / 시스템 B …) 이 상태 버튼 옆에 있음. 기본값 전체
2. 시스템을 고르면 목록이 그 시스템의 요청만 보여 주고 페이지는 1로 돌아감. 상태 필터와 AND
3. 현황 탭도 같은 시스템 선택을 따른다 (총 건수·상태별 카드·유형별 집계가 그 시스템 기준)
4. 선택은 화면을 떠나면 초기화 (전체)

## 5. 상세 요건

| No | 요건 내용 | 필수/선택 | 비고 |
|---|---|---|---|

| 2 | 시스템 선택 시 해당 시스템 요청만 표시. 상태 필터와 AND | 필수 | |

| 6 | 선택한 시스템에 요청이 없으면 빈 상태 문구에 시스템명 표시 | 선택 | 기존 `EmptyState` 사용 |

## 6. 예외 및 특수 상황

| 상황 | 처리 방식 |
|---|---|
