## 1. 서비스 개요

### 1.1 한 줄 정의

리테일 플랫폼 개발팀 **내부용 업무 관리 포탈**. 운영시스템의 변경·배포 요청, 팀 보고(회의록·주간보고·일일점검), 손익, 중점과제·To-Do 를 한곳에서 관리하고 Redmine·Webex 와 연동한다. (현행분석서 1절, `CLAUDE.md` 업무 요건)

### 1.2 해결하는 문제

운영시스템(현재 2개, 추가 예정)의 변경·배포 요청과 팀 보고·손익·과제가 메신저·엑셀·Redmine 에 흩어져 있어 한곳에서 추적·공유할 수 없다.

### 1.3 핵심 가치

요청 → 승인 → 배포 → 보고가 포탈 안에서 끝나고 이력이 남는다. 팀 현황(요청·배포·점검·손익)을 대시보드 한 장으로 본다. Redmine·Webex 같은 기존 도구는 대체하지 않고 연결한다.

## 2. 사용자 및 핵심 시나리오

### 2.1 사용자 유형

(`User.Role` enum, 메뉴 권한 시드, L1 2절, L1 10절 ①④ 결정)

| 사용자 | 설명 | 이 서비스로 하려는 것 |
|---|---|---|
| ADMIN | 플랫폼팀 관리자 | 전체 관리. 사용자·시스템·메뉴 권한, ADMIN 권한 부여 |
| MANAGER | 플랫폼팀 리드 | 요청·배포 승인·반려, 통합 주간보고, 사용자·시스템·메뉴 권한 관리 |
| MEMBER | 플랫폼팀 구성원 | 요청 등록, 담당 시스템 처리, 보고 작성, 과제·To-Do |
| EXTERNAL | 협력사 요청자 | 변경 요청 등록·조회·본인 제출만 (메뉴 1개). 배포는 불가 (①④ 결정) |

### 2.2 핵심 시나리오

(8절 화면 흐름과 7절 API 호출에서 도출, 2026-10-30 확정)

**시나리오 1 — 운영시스템 변경 요청 처리**
```
누가 : MEMBER 또는 EXTERNAL(요청자) → MANAGER → 시스템 담당자(MEMBER)
언제 : 운영시스템에 변경이 필요할 때
1. 요청자가 변경 요청을 등록하고 제출한다 (첨부 포함)
2. MANAGER(또는 담당자)가 승인·반려한다
3. 담당자가 Redmine 일감을 연결해 처리하고 완료 처리한다
결과 : 요청 이력·Redmine 일감·첨부가 포탈에 남고 대시보드에 집계된다
```

**시나리오 2 — 배포 요청과 단계별 배포**
```
누가 : 시스템 담당자(MEMBER) → MANAGER → 담당자
언제 : 승인된 변경을 운영에 배포할 때
1. 담당자가 배포 요청을 등록·제출한다 (Redmine 버전·일감 연결)
2. MANAGER 가 승인하면 배포 단계가 생성된다
3. 담당자가 단계를 하나씩 완료하고, 단계마다 Webex 룸에 알림이 간다
결과 : 마지막 단계 완료로 배포 요청이 완료되고 "전체 배포 완료" 알림이 간다
```

**시나리오 3 — 주간보고와 통합**
```
누가 : MEMBER → MANAGER
언제 : 매주
1. MEMBER 가 개인 주간보고를 쓰며 중점과제·업무단위에 매핑한다
2. 미제출자에게 Webex DM 리마인더가 간다
3. MANAGER 가 통합 주간보고를 만든다
결과 : 주차별 통합 주간보고 1건, 중점과제 실적 탭에 반영
```

**시나리오 4 — 일일점검 보고**
```
누가 : 시스템 담당자(MEMBER)
언제 : 매일 (현재 수동, 향후 자동화 — 4.3 2차)
1. 운영시스템을 고르고 점검 항목 결과를 기록한다
2. 이상이 있으면 변경 요청으로 이어진다 (수동)
결과 : 시스템별 일일점검 이력, 대시보드 집계
```

**시나리오 5 — 운영시스템 추가**
```
누가 : ADMIN / MANAGER
언제 : 관리 대상 운영시스템이 늘어날 때 (현재 2개, 추가 예정)
1. 시스템·서브시스템·서버·담당자를 마스터에 등록한다
2. Redmine 프로젝트 키·Webex 룸을 시스템에 연결한다
결과 : 코드 변경 없이 요청·배포·일일점검·알림이 그 시스템 기준으로 동작한다
```

## 3. 핵심 개념 / 도메인 용어

| 용어 | 정의 | 비고 |
|---|---|---|
| 운영시스템 / 서브시스템 / 서버 | 관리 대상 시스템의 기준 정보 계층. 시스템 담당자가 지정된다 | `operation_systems`, `sub_systems`, `system_servers`, `system_managers` |
| 변경 요청 | 운영시스템 변경을 요청·승인·완료하는 단위. Redmine 일감과 연결 | `change_requests` |
| 배포 요청 / 배포 단계 | 승인된 변경을 운영에 올리는 요청과 그 하위 단계. 단계 완료마다 Webex 알림 | `deploy_requests`, `deploy_steps` |
| 중점과제 → 업무단위 → To-Do | 연간 과제에서 할 일까지 한 업무 사슬 (L1 ⑥ 결정) | `key_tasks`, `work_units`, `todos` |
| 통합 주간보고 | 개인 주간보고를 MANAGER 가 묶은 주차 보고 | `weekly_reports` |
| 일일점검 | 운영시스템별 일일 점검 결과 보고 | `daily_checks` |
| EXTERNAL | 협력사 요청자 계정. 변경 요청 등록·조회·본인 제출만 | L1 ④ 결정 |
| 시스템 담당자 | 운영시스템에 지정된 MEMBER. 요청 처리·배포·일일점검의 주체 | `system_managers` |

## 4. 서비스 범위

### 4.1 제공 기능 (큰 덩어리)

(현행분석서 5절 → L1 3절 A-01~A-12. 전부 운영 중)

| No | 기능 묶음 | 설명 | 제공 시점 |
|---|---|---|---|
| 1 | 변경 요청 관리 (A-03) | 등록·제출·승인·완료, Redmine 일감 연결, 첨부 | 운영 중 |
| 2 | 배포 요청 관리 (A-04) | 등록·승인·단계별 완료, Redmine 버전·일감, Webex 알림 | 운영 중 |
| 3 | 운영시스템 마스터 (A-02) | 시스템·서브시스템·서버·담당자 기준 정보 | 운영 중 |
| 4 | 보고 (A-06-1·2·3) | 회의록, 개인·통합 주간보고(미제출 리마인더), 일일점검 | 운영 중 |
| 5 | 손익 (A-07) | 월별 매출·지출 | 운영 중 |
| 6 | 과제·업무단위·To-Do (A-08) | 중점과제 → 업무단위 → 할 일, 실적 집계 | 운영 중 |
| 7 | 인벤토리 (A-05) | 수주·제안 아이템 | 운영 중 |
| 8 | 대시보드 (A-12) | 요청·배포·점검·손익 집계 | 운영 중 |
| 9 | 계정·권한 (A-01, A-09) | JWT 로그인, 역할 4종, 메뉴 권한 | 운영 중 |
| 10 | 알림·외부 연동 (A-10) | Redmine·Webex·메일 어댑터, 공지 발송 | 운영 중 |
| 11 | AI 기능 (A-11) | 채팅·에이전트·RAG 문서·프롬프트 화면 + 프록시 (AI 서버는 별도) | 구현됨, **운영 미노출** (`VITE_AI_ENABLED` 미설정) |

### 4.2 제외 범위 (Out of Scope)

- Redmine 대체 — 일감 원장은 Redmine, 포탈은 연결만
- AI 서버 자체(모델·RAG·지식베이스·인증) — 별도 시스템과 별도 L1 (⑧ 결정). 포탈은 화면과 프록시까지
- 현업(외부)의 직접 사용 — EXTERNAL 은 협력사 요청자 계정 수준 (④ 결정)
- 인사·근태, 비용 정산, 고객 지원 같은 인접 업무 — 다른 시스템 몫

### 4.3 단계별 제공 계획

| 단계 | 범위 | 목표 시점 |
|---|---|---|
| 1차 (현행) | 4.1 의 1~10 전부, 운영시스템 2개 | 운영 중 (2026-05 착수) |
| 2차 | 일일점검 자동화, 운영시스템 추가, 현행 결함 정리(REQ-2026-001 완료) | 미정 — 운영시스템 추가 요청 시 |
| 이후 | AI 기능 운영 노출 (③ 결정: 사내망 전용 전제) | 미정 — AI 서버 L1 뒤 |

## 6. 제약 및 전제

| 구분 | 내용 |

## 7. 성공 기준
