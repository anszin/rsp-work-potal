## 1. 영역 개요

### 1.1 이 영역의 목적

포탈에 **누가 들어오는지(인증)** 와 **그 사람이 무슨 역할인지(역할·담당자 판정의 원천)** 를 책임진다. 로그인·토큰, 계정 생성·역할·활성 여부·비밀번호 수명주기, 그리고 다른 모든 영역이 쓰는 "현재 사용자·역할·이름" 조회가 여기 속한다. (L1 3절 A-01 "없으면 플랫폼이 동작하지 않음", L1 5절 권한 모델)

### 1.2 범위

| 구분 | 내용 |
|---|---|
| 포함 | JWT 로그인·내 정보 조회·로그아웃(FE), 비밀번호 변경·강제 변경·초기화, 사용자 목록·생성·수정·삭제·활성/비활성, 역할 4종 부여 규칙, 협력사(EXTERNAL) 계정 발급 위임, 초기 관리자 시드, 타 영역용 사용자 조회·역할 판정 공통(`UserLookup`) |
| **제외** | 메뉴 권한 매트릭스(A-09 — 같은 화면의 탭이지만 영역은 별개), 시스템 담당자 지정(A-02 — `system_managers` 는 A-02 소유, A-01 은 판정에 쓰기만), 각 영역의 소유자·담당자 검사 로직 자체(A-03·A-04·A-06·A-08 요건, F-AUTH-001 로 구현됨), 메일 클라이언트(A-10 — 이 영역은 "언제 무엇을 보내나"만), AI 서버 인증(A-11, L1 ③) |

### 1.3 주요 사용자

(서비스정의서 2.1 과 같다. 권한 범위는 L1 10절 ①②④ 결정)

| 사용자 | 이 영역에서 하는 일 |
|---|---|
| 전원 (4역할) | 로그인, 내 정보 확인, 본인 비밀번호 변경, 최초 로그인·초기화 직후 강제 변경 |
| ADMIN | 사용자 전체 관리 + **ADMIN 역할 부여는 ADMIN 만**. ADMIN 계정 신규 생성은 API 로 불가(DB 직접 관리, `UserService.create`) |
| MANAGER | 사용자 생성(MANAGER·MEMBER·EXTERNAL)·수정·삭제·비밀번호 초기화. ADMIN 부여만 불가 |
| MEMBER | 사용자 목록 조회, **EXTERNAL 계정 생성만** (수정·삭제·초기화 불가, 12절 #18 의도) |
| EXTERNAL | 로그인·내 정보·본인 비밀번호 변경만. 사용자 목록도 못 봄(`GET /api/users` 는 ADMIN·MANAGER·MEMBER) |

## 2. 기능 목록

> 기능 ID 는 진척 data.json `meta.abbreviations` 의 `AUTH` 를 그대로 쓴다. F-AUTH-001~005 는 이미 data.json 에 있는 행, 006 은 이 역산에서 식별. 전부 운영 중이며 지금 L3 로 쓸 기능은 없다.

| 기능 ID | 기능 명 | 설명 | 우선순위 | 상세화 단계 | 담당 |
|---|---|---|:---:|:---:|---|
| F-AUTH-001 | 권한·식별 모델 적용 (횡단) | L1 ①②④ 결정의 코드 적용 — 소유자 검사(보고류·To-Do), EXTERNAL 요청자 한정(배포 차단·담당자 판정 제외), 비밀번호 변경 강제 필터, username→이름 매핑 공통(`UserLookup.namesOf/isAdminOrManager`). 거부는 403 통일 | P0 | **L3 확정·구현·배포 완료** (2026-10-21, 수동 검증 5건 미실시) | 안성진 |
| F-AUTH-002 | JWT 로그인·내 정보 | `POST /api/auth/login` → JWT(HS256, 24h, subject=username, role claim 발급만) + `mustChangePassword`. `GET /api/auth/me` 로 새로고침 복원. 비활성 사용자는 로그인·토큰 모두 거부(F-FIX-001 R-004). 토큰은 FE localStorage, 401 이면 인터셉터가 로그아웃 | P0 | L2 (운영 중) | 안성진 |
| F-AUTH-003 | 비밀번호 변경·강제 변경 | 본인 변경(`POST /api/users/change-password`, 현재 비밀번호 확인). `mustChangePassword=true` 면 FE 가드(`PrivateRoute`)가 `/change-password` 로, BE 필터가 허용 경로(auth, change-password, 메뉴 권한 조회) 외 403 `PASSWORD_CHANGE_REQUIRED`. 세션 중 초기화돼도 다음 호출에서 이동(R-010). FE 만 8자 이상 검사 | P0 | L2 (운영 중, F-AUTH-001 R-007·R-010·R-011) | 안성진 |
| F-AUTH-004 | 사용자 관리 | 목록(전체, 정렬 없음), 생성(임시 비밀번호 10자 생성 → 응답·메일, `mustChangePassword=true`), 수정(이름·부서·이메일·역할·활성·Redmine 사용자 ID), 삭제(본인 불가, 요청·배포·담당자 이력 있으면 "비활성화하세요" 안내 — F-FIX-001 R-006), 비밀번호 초기화(임시 비밀번호 재발급). `username` 은 생성 후 변경 불가(수정 API 에 없음, L1 ②) | P0 | L2 (운영 중) | 안성진 |
| F-AUTH-005 | 협력사 계정 발급 위임 | MEMBER 가 EXTERNAL 계정을 생성할 수 있다(그 외 역할은 거부). 화면은 MEMBER 에게 역할 선택지를 EXTERNAL 로 고정. 생성 뒤 관리는 ADMIN·MANAGER 만 | P1 | L2 (운영 중, 12절 #18 의도, L1 ④ 유지) | 안성진 |
| F-AUTH-006 | 초기 관리자 시드 | 기동 시 `admin` 계정이 없으면 생성(역할 ADMIN, 비밀번호 `admin123!` 하드코딩, 기동 로그에 출력 — 현행분석서 11절 비밀값). `mustChangePassword` 는 false 라 강제 변경 안 걸림 | P2 | L2 (운영 중, **9절 미결정**) | 안성진 |

**상세화 단계 기준**

| 수준 | 의미 | 개발 착수 |
|:---:|---|:---:|
| L1 | 기능 이름만 식별됨 | ✗ |
| L2 | 기능 정의 + 데이터 개요 완료 | ✗ |
| L3 | 처리 규칙 + 인수 조건 확정 | ✓ |

> ※ 운영 중 기능은 현행 동작이 곧 규칙이다. 변경이 생길 때 그 기능만 L3 로 쓴다. 9절의 비밀값·라우트 가드 항목은 설계 결정(DEC) 뒤 요건요청서 → L3 경로.

## 3. 업무 흐름

### 3.1 주요 시나리오

**시나리오 1 : 계정 발급 → 최초 로그인 → 비밀번호 변경**
```
1. MANAGER(또는 MEMBER, EXTERNAL 한정)가 사용자 등록 → 임시 비밀번호가 화면 모달과 메일(이메일 있을 때)로 전달. mustChangePassword=true
2. 사용자가 임시 비밀번호로 로그인 → 응답 mustChangePassword=true → /change-password 로 이동
3. 다른 URL 을 쳐도 FE 가드가 되돌리고, API 를 직접 불러도 BE 필터가 403 PASSWORD_CHANGE_REQUIRED
4. 현재(임시)·새 비밀번호 입력 → 변경 → mustChangePassword=false → /me 재조회 → 대시보드
```

**시나리오 2 : 매 요청 인증과 역할·담당자 판정 (다른 영역이 쓰는 흐름)**
```
1. FE axios 인터셉터가 Authorization: Bearer <JWT> 부착
2. JwtAuthFilter: 서명·만료 검증 → username 으로 DB 재조회 → active=false 면 익명 처리 → mustChangePassword 면 허용 경로 검사 → SecurityContext(ROLE_<역할>)
3. 컨트롤러 @PreAuthorize(역할) 또는 서비스 내 판정(UserLookup.isAdminOrManager, A-02 담당자 여부)
4. 401 → FE 가 토큰 삭제·로그인 화면. 403 → 화면이 오류 메시지 표시
```

**시나리오 3 : 사용자 비활성화·삭제**
```
1. ADMIN/MANAGER 가 사용자 수정에서 활성 해제 → 이후 로그인 불가, 기존 토큰도 거부
2. 삭제 시도 → 변경·배포 요청 또는 담당자 이력이 있으면 400 "비활성화하세요" / 없으면 물리 삭제
3. 보고류·To-Do 는 username 문자열 참조라 삭제 뒤에도 남고, 이름 매핑만 빈 값 (L1 ②)
```

### 3.2 상태 전이

사용자 계정의 상태는 두 플래그의 조합이다 (`User.active`, `User.mustChangePassword`). 상태 기계 코드는 없고 각 API 가 플래그를 바꾼다.

| 상태 | 설명 | 다음 가능 상태 | 전이 조건 |
|---|---|---|---|
| 신규 (active, 변경 필요) | 생성 직후. 로그인은 되나 비밀번호 변경 외 차단 | 정상 | 본인 비밀번호 변경 |
| 정상 (active) | 전 기능 사용 | 변경 필요 / 비활성 / 삭제 | 초기화(ADMIN·MANAGER) / 활성 해제 / 삭제(이력 없을 때) |
| 변경 필요 (active, 초기화됨) | 세션 중이면 다음 호출에서 /change-password 로 | 정상 | 본인 비밀번호 변경 |
| 비활성 (inactive) | 로그인·토큰 거부. 알림·리마인더 대상에서도 제외 | 정상 / 삭제 | 활성 복구 / 삭제(이력 없을 때) |

## 4. 데이터 모델

### 4.1 엔티티

(`BE/domain/user/entity/User.java`, `BE/security/*`)

| 엔티티 | 설명 | 주요 항목 | 비고 |
|---|---|---|---|
| 사용자 (User) | 계정 1건 | `username`(unique, **불변 = 정식 식별자**), 이름, 부서, 이메일(unique, 선택), 비밀번호(BCrypt), 역할(enum 4), 활성, 비밀번호 변경 필요, Redmine 사용자 ID, 생성 시각 | `updatedAt` 없음. 마지막 로그인·비밀번호 변경 시각 없음(7절 감사 로그) |
| 인증 토큰 (JWT, 비영속) | 로그인 결과 | subject=username, role claim(발급만, 검증·인가에 미사용 — DEC-AS-03), iat, exp(24h) | 서버 저장 없음(stateless). 강제 만료·블랙리스트 없음 → 비활성화는 매 요청 DB 재조회로 막음 |
| 인증 주체 (PortalUserDetails, 비영속) | 요청 처리 중 사용자 | username, enabled(=active), mustChangePassword, `ROLE_<역할>` | F-AUTH-001 R-007 |

### 4.2 엔티티 관계

```
사용자 1 ─── N 변경 요청 [A-03] (requester, FK)
사용자 1 ─── N 배포 요청 [A-04] (requester·approver, FK)
사용자 1 ─── N 시스템 담당자 [A-02] (system_managers.user_id, FK)
사용자 (username 문자열) ← 주간보고·회의록 author, 일일점검 reporter [A-06], To-Do assignee·collaborators [A-08], 배포 단계 completedBy [A-04]
역할(enum) ← 메뉴 권한 [A-09] (role 컬럼)
```

FK 3곳이 삭제를 막는 이력이고, 문자열 참조는 이력으로 보지 않는다(L1 ②, F-FIX-001 R-006).

### 4.3 기준 정보 / 코드

| 코드 구분 | 값 | 관리 주체 |
|---|---|---|
| 역할 | ADMIN, MANAGER, MEMBER, EXTERNAL(=협력사 요청자) | 코드(enum). 화면 라벨 관리자/매니저/팀원/외부팀원 |
| 역할 부여 규칙 | ADMIN 생성 불가(API), ADMIN 부여는 ADMIN 만, MEMBER 는 EXTERNAL 만 생성, EXTERNAL 은 생성 불가 | 코드(`UserService.create/update`) |
| 비밀번호 변경 전 허용 경로 | `/api/auth/**`, `POST /api/users/change-password`, `GET /api/menu-permissions` | 코드(`JwtAuthFilter`) |
| 임시 비밀번호 | 영숫자 10자(혼동 문자 제외), `SecureRandom` | 코드 |
| 토큰 만료 | `jwt.expiration` 기본 24h, 비밀키 `JWT_SECRET`(yml 기본값 평문 — 9절) | 서버 설정 |

## 5. 영역 간 인터페이스

### 5.1 이 영역이 제공하는 것

| 제공 대상 영역 | 제공 내용 | 방식 |

| A-03·A-04·A-06·A-08 | "ADMIN 또는 MANAGER" 판정, username 집합 → 이름 매핑 | `UserLookup.isAdminOrManager / namesOf / nameOf` |

| A-10 알림·연동, A-06-2 리마인더 | 활성·역할·이메일로 수신자 선별(EXTERNAL 제외) | `UserRepository.findAll()` 뒤 필터(`NotificationService`, `WeeklyReportReminderScheduler`) |
| A-09 | 역할 enum | `User.Role` |
| FE 전역 | `token`, `user`(이름·역할·mustChangePassword), 로그아웃, `refreshMe` | `AuthContext` |

### 5.2 이 영역이 필요로 하는 것

| 제공 영역 | 필요 내용 | 없을 때 대응 |
|---|---|---|

## 7. 비기능 요건

| 항목 | 기준 | 확정 |
|---|---|:---:|
| 응답 시간 | 로그인은 BCrypt 1회 + DB 조회. 매 요청 DB 재조회 1회(`findByUsername`) — 사용자 수십 명 규모에서 문제 없음 | ☑ (현행) |
| 동시 사용자 | 플랫폼팀 + 협력사 요청자(수십 명). 세션 서버 상태 없음 | ☑ (현행) |
| 데이터 규모 | 사용자 수십 건. `미조사` | ☑ (현행) |
| 오프라인 동작 | 없음 | ☑ |
| 권한 / 접근 제어 | L1 ①②④ 확정. 인가 방식은 `@PreAuthorize`(역할) + 서비스 내 판정(소유자·담당자) — F-AUTH-001 부분 적용, 통일(DEC-AS-04)은 설계 단계. 라우트 가드는 토큰 유무만(DEC-AS-07) | ☑ (현행) / 통일은 설계 |
| 비밀번호 | BCrypt 저장. 규칙은 FE 8자 이상만, BE 검증 없음. 임시 비밀번호 10자 | ☐ (9절) |
| 토큰 | HS256 24h, 갱신 없음(만료 시 재로그인), 서버측 폐기 없음. 비밀키는 환경변수 `JWT_SECRET`(기본값 평문) | ☑ (현행) / 비밀키 기본값은 9절 |
| 데이터 보존 기간 | 이력 없는 사용자만 물리 삭제, 나머지는 비활성화. 보고류 문자열 참조는 영구 | ☑ (L1 ②) |
| 감사 로그 | 생성 시각만. 로그인 성공·실패, 비밀번호 변경·초기화, 역할 변경, 활성 변경 이력 없음 | ☐ (L1 5절 로그/감사 정책 → 설계 단계) |

## 9. 미결정 사항

| 항목 | 미결정 사유 | 영향 기능 | 결정 필요 시점 |
|---|---|---|---|
| 임시 비밀번호 노출 경로 | 생성·초기화 응답(`tempPassword`)과 메일 본문에 평문. 화면 모달 표시가 운영 전제라 응답 제거 시 전달 수단이 메일뿐이 됨. 선택지: (a) 현행 유지 (b) 응답은 1회 표시 후 폐기·메일 제거 (c) 초기화 링크 방식 | F-AUTH-004·005 | **설계 단계** (rsp-design-arch, 보안 점검 2026-10-28 조치 항목과 함께) |
| 초기 관리자 비밀번호 | `admin123!` 하드코딩 + 기동 로그 출력, `mustChangePassword=false`. 제안: 환경변수 주입 + 최초 기동 시 변경 강제 | F-AUTH-006 | **설계 단계** (build.md 비밀값 주입 결정과 함께) |
| JWT 비밀키·만료 기본값 | `JWT_SECRET` yml 기본값이 평문으로 저장소에 있음. 운영은 환경변수로 덮는지 `확인 필요` | F-AUTH-002 | **설계 단계** (같은 건) |
| 라우트 가드 범위 (DEC-AS-07) | 역할·메뉴 권한은 메뉴 숨김뿐. MEMBER 가 `/admin/users` 에 URL 로 진입 가능(등록만 허용되므로 실해는 없음). 역할별 라우트 가드를 둘지 | S-03, 전 화면 | **설계 단계** (design.md) |
| 비밀번호 규칙 BE 검증 | FE 8자 이상만. BE 는 길이·복잡도 검사 없음(API 직접 호출 시 1자도 가능) | F-AUTH-003 | 다음 A-01 변경 때 (L3 에서 규칙 확정) |
| 로그인·권한 변경 감사 이력 | 7절 감사 로그 항목 | F-AUTH-002·004 | **설계 단계** (L1 5절 로그/감사 정책) |
| JWT role claim 미사용 (DEC-AS-03) | 발급만 하고 인가는 매 요청 DB 재조회. 제거할지 활용할지 | F-AUTH-002 | **설계 단계** |

> ※ 데이터 모델(4절)·인터페이스(5절)의 미결정은 없다 → rsp-design-arch 착수 가능. 위 항목은 전부 설계 결정이거나 L3 규칙이며, 설계 단계 항목은 architecture.md·build.md·design.md 미결정 표에 항목으로 올려 J-05 추적 대상으로 만든다.
