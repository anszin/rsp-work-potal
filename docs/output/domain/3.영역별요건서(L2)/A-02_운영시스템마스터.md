## 1. 영역 개요

### 1.1 이 영역의 목적

관리 대상 **운영시스템의 기준 정보 계층(시스템 → 서브시스템 → 서버)과 시스템 담당자**를 보관해, 변경 요청·배포 요청·일일점검·알림이 "어느 시스템 기준으로" 동작하는지 정한다. 시스템을 추가하면 코드 변경 없이 요청·배포·점검·알림이 그 시스템으로 동작해야 한다. (L1 3절 A-02, 서비스정의서 시나리오 5·성공 기준 2)

### 1.2 범위

| 구분 | 내용 |
|---|---|
| 포함 | 운영시스템 등록·수정·삭제·활성/비활성·정렬, 서브시스템 등록·수정·삭제·활성, 서브시스템별 배포 서버 등록·삭제(단계 순서), 시스템 담당자 지정·해제, 타 영역용 조회(전체·활성·담당 시스템·활성 서브시스템), 시스템별 연동 키(Redmine 프로젝트 키·Webex 룸 ID) 보관, 초기 시스템 시드 |
| **제외** | 담당자 권한 판정 결과의 사용(A-03·A-04 가 `existsBySystemIdAndUserId` 로 직접 판정), Redmine 트래커·상태 목록(서버 설정 `redmine.trackers`, A-10), Redmine·Webex 호출 자체(A-10), 배포 단계 생성·완료(A-04 — 서버 목록을 복사해 갈 뿐), 사용자 계정(A-01) |

### 1.3 주요 사용자

| 사용자 | 이 영역에서 하는 일 |
|---|---|
| ADMIN / MANAGER | 시스템·서브시스템·서버·담당자 전부 등록·수정·삭제 (쓰기 API 전부 `@PreAuthorize ADMIN, MANAGER`) |
| MEMBER | 조회만. 변경·배포·일일점검 화면의 시스템 Select, 담당 시스템 기본값(`/systems/managed`) |
| EXTERNAL | 조회만 — 변경 요청 등록용 활성 시스템·서브시스템 Select. 담당자로 등록돼도 무시(L1 ④). 서버·담당자 목록도 API 로는 조회 가능(권한 없음, 현행분석서 11절 — 9절) |

| 수준 | 의미 | 개발 착수 |

## 3. 업무 흐름

### 3.1 주요 시나리오

**시나리오 1 : 운영시스템 추가 (서비스정의서 시나리오 5)**
```
1. ADMIN/MANAGER 가 시스템 등록 — 코드·이름·Redmine 프로젝트 키·Webex 룸 ID·정렬
2. 하위시스템 관리 모달에서 서브시스템 등록 → 서버 관리 모달에서 배포 서버를 순서대로 등록
3. 담당자 관리 모달에서 MEMBER 를 담당자로 지정
4. 결과: 변경·배포·일일점검 화면 Select 에 즉시 노출(활성). 변경 요청은 프로젝트 키로 Redmine 일감 생성, 배포 승인 시 서버 수만큼 단계 생성, 알림은 그 시스템 룸으로. 코드 변경 없음 ✓
   (단, Redmine 트래커·상태 목록은 서버 설정 redmine.trackers 공용 — 시스템별 아님)
```

**시나리오 2 : 시스템 비활성화 vs 삭제**
```
1. 더 이상 쓰지 않는 시스템 → 수정에서 활성 해제 → /systems/active 에서 빠져 새 요청 등록 불가, 기존 요청·배포·점검 이력은 그대로 조회
2. 삭제 → deleteById 만 실행. 변경·배포·일일점검·담당자 FK 가 하나라도 있으면 DB 제약 위반 500 (A-01 사용자 삭제 #22 와 같은 구조, 사용자 쪽만 R-006 으로 안내 처리됨 — 9절)
```

**시나리오 3 : 담당자 지정이 권한으로 이어지는 흐름 (A-03·A-04 가 쓰는 흐름)**
```
1. 담당자 지정 → system_managers(system_id, user_id) 1행
2. A-03·A-04 서비스가 상태 전환 때 existsBySystemIdAndUserId(system, actor) 로 판정, actor 역할이 MEMBER 일 때만 유효(EXTERNAL 제외, F-AUTH-001 R-004·R-005)
3. FE 는 /systems/managed 로 내 담당 시스템 ID 를 받아 필터 기본값(담당 1개면 그것)
```

### 3.2 상태 전이

| 상태 | 설명 | 다음 가능 상태 | 전이 조건 |
|---|---|---|---|
| 활성 (시스템·서브시스템) | Select 노출, 새 요청·점검 등록 가능 | 비활성 / 삭제 | ADMIN·MANAGER 수정 / 삭제(참조 없을 때만 성공) |
| 비활성 | Select 에서 제외. 기존 데이터 유지. 전체 목록(`/systems`)·관리 화면에는 표시 | 활성 / 삭제 | 수정 / 삭제 |

서버·담당자는 상태 없음(존재/삭제뿐).

## 4. 데이터 모델

### 4.1 엔티티

(`BE/domain/system/entity/`)

| 엔티티 | 설명 | 주요 항목 | 비고 |
|---|---|---|---|
| 운영시스템 (OperationSystem) | 관리 대상 시스템 | 코드(unique, 20자), 이름, 설명, Redmine 프로젝트 키, Webex 룸 ID, 정렬 순서, 활성, 생성 시각 | `updatedAt` 없음. 코드는 수정 API 에 없음(불변) |
| 서브시스템 (SubSystem) | 시스템 하위 구분 | 시스템[FK], 코드(시스템 내 unique), 이름, 설명, 활성, 생성 시각 | 변경·배포 요청이 선택적으로 참조 |
| 배포 서버 (SystemServer) | 서브시스템의 배포 단계 원천 | 서브시스템[FK], 서버명, 단계 순서 | 생성 시각 없음. A-04 DeployStep 이 승인 시 복사 |
| 시스템 담당자 (SystemManager) | 시스템 × 사용자 | 시스템[FK], 사용자[A-01 FK], 지정 시각. unique(system, user) | 역할 검사 없이 누구나 등록 가능(EXTERNAL 포함), 판정 때 제외 |

### 4.2 엔티티 관계

```
운영시스템 1 ─── N 서브시스템 1 ─── N 배포 서버
운영시스템 1 ─── N 시스템 담당자 N ─── 1 사용자 [A-01]
운영시스템 1 ─── N 변경 요청 [A-03], 배포 요청 [A-04], 일일점검 [A-06-3]
서브시스템 1 ─── N 변경 요청 [A-03] (선택), 배포 요청 [A-04] (선택)
운영시스템.redmine_project_key → Redmine 프로젝트 [A-10]
운영시스템.webex_room_id → Webex 룸 [A-10] (없으면 서버 설정 기본 룸)
```

### 4.3 기준 정보 / 코드

| 코드 구분 | 값 | 관리 주체 |
|---|---|---|
| 시스템 코드 | 자유 문자열 20자(현행 `SYS001` 형식 시드, 규칙 강제 없음) | 사람 입력 |
| 정렬 | `sortOrder` 오름차순 → id. 기본 0 | 사람 입력 |
| 단계 순서 | `stepOrder`, 0 이면 "현재 서버 수"로 자동 | 코드 |
| Redmine 트래커·상태 | 서버 설정 `redmine.trackers`(공용), `redmine.cr-tracker-id` | 서버 설정 (A-10) — 시스템별 분리는 요건 없음 |
| 기본 Webex 룸 | `webex.room-id` | 서버 설정 (A-10) |

> 삭제 실패(FK) 는 서브시스템·서버만 `alert(apiError)` 처리, 시스템 삭제는 오류 표시 없음(`deleteMut` onError 없음) — `확인 필요`: 500 시 화면 반응.

## 9. 미결정 사항

| 항목 | 미결정 사유 | 영향 기능 | 결정 필요 시점 |
|---|---|---|---|
| 시스템·서브시스템 삭제 시 참조 검사 | 변경·배포·일일점검·담당자 이력이 있으면 500. 사용자 삭제는 R-006 으로 "비활성화하세요" 안내 처리했으나 시스템은 미처리. 제안: 같은 패턴(이력 있으면 400 안내, 비활성화 유도) | F-SYS-001 | 다음 A-02 변경 때 (요청서 → L3. DEC 변경 없음) |
| EXTERNAL 의 A-02 조회 범위 | 활성 시스템·서브시스템은 변경 요청 등록에 필요. 서버·담당자 목록·전체 시스템(비활성 포함)은 불필요하나 API 는 열려 있음. 제안: 조회도 역할×API 매트릭스에 포함 | F-SYS-004 | **설계 단계** (DEC-AS-04 인가 통일, api.md "인가 규칙 명세" 미결정과 같은 건) |
| 담당자 후보에서 EXTERNAL 제외 | L1 ④ 로 EXTERNAL 담당자는 판정에서 무시되는데 화면·API 는 등록을 허용. 제안: 등록 자체를 거부(400) 또는 후보 Select 에서 제외 | F-SYS-003 | 다음 A-02 변경 때 (위 삭제 검사와 같은 L3 에 묶음 가능) |
| 서버 수정·순서 변경 | 서버는 삭제 후 재등록만. 배포 단계가 이미 복사된 뒤에는 영향 없음 | F-SYS-002 | 요구가 생길 때 |
| Redmine 트래커 설정의 시스템별 분리 | 현행 공용(`redmine.trackers`). 두 번째 이후 시스템이 다른 트래커 체계를 쓰면 필요 | F-SYS-001, A-03·A-10 | 운영시스템 추가 요청 때 (서비스정의서 9절 미결정과 같은 시점) |

> ※ 데이터 모델(4절)·인터페이스(5절)의 미결정은 없다 → rsp-design-arch 착수 가능. 설계 단계 항목(EXTERNAL 조회 범위)은 api.md 미결정 표의 "인가 규칙 명세" 행에 묶는다.
