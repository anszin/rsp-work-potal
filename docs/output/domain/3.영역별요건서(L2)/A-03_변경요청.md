## 1. 영역 개요

### 1.1 이 영역의 목적

운영시스템에 대한 변경 요청을 **등록 → 제출 → 승인/반려 → 완료** 로 기록하고, Redmine 일감으로 연결해 일감 원장과 맞춘다. 현업(EXTERNAL)이 포탈에서 쓰는 유일한 기능이다. (L1 3절 A-03, 서비스정의서 시나리오 1)

### 1.2 범위

| 구분 | 내용 |
|---|---|
| 포함 | 변경 요청 등록·수정·삭제, 첨부(링크 또는 파일 1개), 상태 전환(제출·승인·반려·완료), Redmine 일감 생성·갱신·재동기화, 목록 조회·필터, 현황 집계 |
| **제외** | 운영시스템·담당자 기준 정보(A-02), Redmine 클라이언트 자체(A-10, 이 영역은 "언제 무엇을 만드나"만), 배포 요청(A-04) — 변경 요청과 데이터로 연결되지 않음(A-04 L2 9절 미결정과 같은 건), 대시보드 카드(A-12) |

### 1.3 주요 사용자

| 사용자 | 이 영역에서 하는 일 |
|---|---|
| 요청자 (MEMBER 또는 EXTERNAL) | 등록, 초안 수정·삭제, 첨부, **본인 요청 제출**(ADMIN 도 남의 것은 제출 못 함, 12절 #14 의도) |
| 시스템 담당자 (MEMBER, `system_managers`) | 담당 시스템 요청의 승인·반려·완료 |
| MANAGER / ADMIN | 모든 시스템의 승인·반려·완료 |
| EXTERNAL | 등록·조회·본인 제출만. 승인·완료 불가, 담당자로 등록돼도 무시 (L1 ④, F-AUTH-001 R-005). 메뉴는 이것 하나 |

## 2. 기능 목록

> 기능 ID 는 진척 data.json `meta.abbreviations` 의 `CR` 을 그대로 쓴다. F-CR-001~003 은 이미 data.json 에 있는 행(전부 운영 중), 004~005 는 이 역산에서 식별. **F-CR-004 가 REQ-2026-003.**

| 기능 ID | 기능 명 | 설명 | 우선순위 | 상세화 단계 | 담당 |
|---|---|---|:---:|:---:|---|
| F-CR-001 | 변경 요청 등록·수정·삭제·첨부 | 시스템·서브시스템·제목·내용·요청 부서/담당자·희망일·Redmine 트래커/담당자. 번호 `CR-YYYY-NNN`(MAX+1, F-FIX-001 R-002). 첨부는 링크 또는 파일 1개(Base64 JSON 업로드, 서버 저장, 다운로드·삭제). 초안만 수정·삭제 | P0 | L2 (운영 중) | 안성진 |
| F-CR-002 | 변경 요청 상태 전환 | 초안→요청→승인/반려→완료. 제출 = 요청자 본인만, 승인·반려·완료 = 담당자(MEMBER)∥관리자. 상태별 시각·코멘트·반려 사유 기록. Webex 알림 없음(배포와 다름) | P0 | L2 (운영 중, F-AUTH-001 R-005) | 안성진 |
| F-CR-003 | Redmine 일감 연결 | 등록 시 시스템 프로젝트 키로 일감 생성(트래커·담당자·희망일), 초안 수정 시 일감 갱신, 실패 시 FAILED 기록 후 재동기화. 프로젝트 키 없으면 SKIPPED | P0 | L2 (운영 중) | 안성진 |
| **F-CR-004** | **목록 조회·시스템별 필터** | 목록·상태 필터·페이지네이션에 **운영시스템 Select(활성만, 기본 전체)** 추가. 상태 필터와 AND, 선택 시 1페이지. 현황 탭도 같은 선택. A-04 F-DR-006 과 같은 Select 패턴 | P1 | **L2 → L3 예정 (REQ-2026-003)** | 안성진 |
| F-CR-005 | 변경 요청 현황 집계 (현황 탭) | 전체·상태별 카드, 시스템별 건수 막대. 기간 선택 없음(배포 현황과 다름) | P2 | L2 (운영 중) | 안성진 |

**상세화 단계 기준**

| 수준 | 의미 | 개발 착수 |
|:---:|---|:---:|
| L1 | 기능 이름만 식별됨 | ✗ |
| L2 | 기능 정의 + 데이터 개요 완료 | ✗ |
| L3 | 처리 규칙 + 인수 조건 확정 | ✓ |

> ※ 운영 중 기능(001~003·005)은 현행 동작이 곧 규칙이므로 변경이 생길 때 그 기능만 L3 로 쓴다. 지금 L3 를 쓰는 것은 F-CR-004 뿐.

## 3. 업무 흐름

### 3.1 주요 시나리오

**시나리오 1 : 현업 요청 → 처리 (서비스정의서 시나리오 1)**
```
1. 요청자(EXTERNAL 또는 MEMBER)가 변경 요청 등록 (첨부 포함) → 초안. Redmine 일감 자동 생성(프로젝트 키 있을 때)
2. 요청자 본인이 제출 → REQUESTED
3. 담당자 또는 관리자가 승인(또는 반려·사유) → APPROVED
4. 담당자가 처리 후 완료 → COMPLETED. 일감은 Redmine 에서 별도 관리
```

**시나리오 2 : 초안 수정과 Redmine 갱신**
```
1. 초안 상태에서 제목·내용·희망일·담당자 수정
2. 이미 생성된 Redmine 일감이 있으면 제목·내용·트래커·담당자·희망일을 함께 갱신 (실패해도 수정은 저장)
3. 동기화 실패 건은 상세에서 "재동기화"
```

**시나리오 3 : 담당 시스템만 보기 (F-CR-004, 이번 요청)**
```
1. 변경 관리 진입 → 시스템 Select 기본 "전체"
2. 자기 시스템 선택 → 목록·페이지 1·현황 탭 집계가 그 시스템 기준
3. 상태 버튼과 조합
```

### 3.2 상태 전이

(`ChangeRequestService.ALLOWED_TRANSITIONS`, `changeStatus`)

| 상태 | 설명 | 다음 가능 상태 | 전이 조건 |
|---|---|---|---|
| DRAFT | 초안. 수정·삭제·첨부 변경 가능 | REQUESTED | 요청자 본인 |
| REQUESTED | 제출됨, 처리 대기 | APPROVED, REJECTED | 담당자(MEMBER)∥관리자 |
| APPROVED | 승인됨, 처리 중 | COMPLETED | 담당자∥관리자 |
| REJECTED | 반려(사유 기록) | — | 종료 |
| COMPLETED | 완료(completedAt) | — | 종료 |

배포 요청과 달리 서버 단계가 없고, 완료는 사람이 직접 전환한다.

## 4. 데이터 모델

### 4.1 엔티티

(`BE/domain/request/entity/`)

| 엔티티 | 설명 | 주요 항목 | 비고 |
|---|---|---|---|
| 변경 요청 (ChangeRequest) | 요청 1건 | 번호 `CR-YYYY-NNN`, 시스템·서브시스템[외부 A-02], 제목, 내용, 요청자[외부 A-01], 요청 부서·담당자명(텍스트), 희망일, 첨부(링크 / 서버 경로·원본명), 상태, 반려 사유·처리 코멘트, 요청·승인·완료 시각, Redmine 트래커·담당자 ID, 동기화 상태 | 승인자 컬럼 없음(배포와 다름 — `확인 필요`: 누가 승인했는지 기록할 필요) |
| 변경 요청 일감 (ChangeRequestIssue) | 요청에 묶인 Redmine 일감 | Redmine 일감 ID·제목 | 등록 시 자동 생성 1건. 수동 선택 없음(배포와 다름) |

### 4.2 엔티티 관계

```
운영시스템[A-02] 1 ─── N 변경 요청
서브시스템[A-02] 1 ─── N 변경 요청 (선택)
사용자[A-01]     1 ─── N 변경 요청 (요청자)
변경 요청        1 ─── N 변경 요청 일감 (현행은 1건)
```

### 4.3 기준 정보 / 코드

| 코드 구분 | 값 | 관리 주체 |
|---|---|---|
| 상태 | DRAFT, REQUESTED, APPROVED, REJECTED, COMPLETED | 코드(enum) |
| Redmine 동기화 | SYNCED, FAILED, SKIPPED | 코드(enum) |
| Redmine 트래커·담당자 | 시스템별 트래커 설정(`trackerConfigs`), 기본 트래커 `redmine.cr-tracker-id` | A-02 설정 + 서버 설정 |
