## 2. 요청 배경 및 목적

### 2.1 요청 배경

운영 중인 업무 포탈을 rsp-ai-dlc 방법론으로 현행 분석한 결과(`docs/7.현행분석서.md`), 코드가 의도와 다르게 동작하는 결함 8건이 확인됐다. 그중 6건은 권한 모델 결정 없이 고칠 수 있는 1~10줄 수정이다.

### 2.2 기대 효과

- 일일점검 화면이 실제로 쓰일 수 있게 됨 (시스템 선택이 비어 있던 문제)
- 변경요청 등록이 번호 충돌로 실패하는 일이 없어짐
- 비활성화한 사용자가 실제로 차단됨
- 사용자 삭제·서버 삭제가 오류 대신 안내 메시지를 줌
- 메일 발송 실패가 로그에 남음
- 부수 효과: 테스트 0건인 백엔드에 첫 테스트(현행 동작 고정) 도입

## 4. 업무 흐름

### 4.1 현재 업무 흐름 (As-Is)

1. 일일점검 → 등록 → **시스템 선택이 비어 있음** (화면이 `/api/api/systems` 호출)
2. 변경요청 등록 → 중간 번호를 지운 적이 있으면 **"등록 실패(500)"** 가 건수가 따라잡을 때까지 반복
3. 사용자 관리 → 비활성화 → **그 사용자는 여전히 로그인·사용 가능**
4. 사용자 관리 → 삭제 → 요청·배포·담당자 이력이 있으면 **500 오류**, 이유 안내 없음
5. 시스템 관리 → 서버 삭제 → **다른 서브시스템의 서버 ID 로도 삭제됨** (관리자 한정)
6. 계정 생성·비밀번호 초기화 → 메일 실패 시 **아무 기록 없음**

### 4.2 변경 후 업무 흐름 (To-Be)

1. 일일점검 등록 폼에 활성 시스템 목록 표시
2. 변경요청 번호는 삭제와 무관하게 항상 그 해 최대값+1
3. 비활성 사용자는 로그인 불가(401), 기존 토큰도 무효(403)
4. 이력 있는 사용자 삭제 시 "이력이 있어 삭제할 수 없습니다. 비활성화하세요." (400)
5. 서버 삭제 시 서브시스템 소속 확인, 불일치면 400
6. 메일 실패 시 warn 로그 (동작은 그대로 성공 처리)
